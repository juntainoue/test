## 画面の流れ

「🧺 使い切り計画」タブ（最初に表示）と「📖 レシピ」タブの2つ。開いてすぐ料理の写真を選べるよう、上部の大きな見出し画像は削除した。手順は「1. 食べたい料理」「2. 条件（初期値のままでよい）」「3. 自宅の食材」の順。以前の「おまかせ献立」とその買い物リストは、依頼者の判断で削除した（2026-11-11。保存データ `gohan-keikaku-v1` は削除せず残す）。

1. **条件**: 計画日数（1〜7日）、調理時間（指定なし／15・20・30・45分以内）、冷凍（できる／できない）、作り置き（しない／してもよい）、同じ料理（繰り返さない／繰り返してもよい）。サービス側で一律に決めない。
2. **食べたい料理**: 料理の写真カードから1品選ぶ（作った記録・お気に入り・写真ありの順に先頭へ。最初は12品、「もっと見る」で全件）。調理時間の条件で候補を絞り、条件を超える料理を後から選んだ場合は注意を表示する。料理を選ぶまで「仮の献立をつくる」は押せない。
3. **自宅の食材**: 名前だけで追加。レシピの材料名と一致しない場合は近い名前を候補として示し、自動では選ばない（例：「鶏肉」→ 鶏もも肉／鶏むね肉／鶏ひき肉）。「今回使う」のチェックで、献立に入れたい食材を指定する。量・期限は聞かない。
4. **仮の献立**: 選んだ料理を1日目に固定し、残りの日を組む。日ごとに写真と「使い回す食材」を表示する。「この日だけ交換」は、食材を使い回しやすい順に最大6品の写真候補を出し、利用者が選ぶ。
5. **買い物リスト（タップで選ぶ）**: 食材ごとに「ちょうど必要な量」と、よくあるパック量（必要量の0.5〜4倍の範囲で最大4つ）をボタンで表示し、タップで買う量を決める。個数で買う食材（個・本・片など）は必要数を切り上げた数が「ちょうど」になり、「個数で買う◯品を必要な数にする」で一括入力できる。ほかの量は「ほかの量」から入力（単位は材料の単位に固定）、量が書かれていないパックは「量がわからない」（残りは計算しない）。調味料・主食は入力欄なしの一覧。自宅の食材は「家の分で足りる」「足りないので買う」をタップ（未選択は「足りるか未確認」）。ボタンの量は候補を示すだけで、利用者が選ぶまで何も仮定しない。
6. **パック量に合わせて組み直す**: 入力した購入量を基に、余りが出ない・不足しない組み合わせを探す。
7. **残る食材の確認**: 不足、使い切れない食材（量・保存案・その残りで作れる料理の例）、残りを計算できていない食材、自宅の食材の扱いを表示する。

## 決定事項（要件で未決定だった点）

- **最初に選んだ料理は、交換・作り直し・組み直しのすべてで1日目に固定する。** その日の「この日だけ交換」は使えず、「2. 食べたい料理」で選び直すよう案内する。
- **作り置き**は「同じ料理を2日分まとめて作り、翌日はそれを食べる」と定義した。保存目安に「作りたて」「当日中」「翌日中」「作り置きはしない」などとある料理は作り置きにしない。AI提案の料理も作り置きにしない。
- 作り置きは利用者が明示的に選ぶため、「同じ料理を繰り返さない」設定でも作り置きによる2日連続は許可する（画面に「2日分まとめて作る」「前日の作り置きを食べる」と表示）。
- **定番と新しい料理**: 「定番」は、このアプリで「作った」と記録した料理とお気に入り。記録が1件もない間は区別しない（ラベルも出さない）。記録がある場合は、新しい料理を `max(1, floor(日数/3))` 品までに抑え、3日以上なら1品は入れるよう評価する。記録のない料理は「調理記録なし」と表示し、「未経験」とは断定しない。
- 人数は1人分固定（初版の検証範囲）。以前の「おまかせ献立」の人数変更（1〜4人）は、画面の削除に伴い使えなくなった。

## 数量計算（プログラムで行う）

`js/ingredients.js` の `buildLedger` が、献立・購入量・自宅の食材から食材ごとの表を作る。

- 食材は「正規化した名前＋単位」で合算する。正規化は全角半角・空白・カタカナ→ひらがな・表記ゆれ（玉子→卵、人参→にんじん等）。
- **単位が違うものは合算も換算もしない**（卵「個」と卵「g」は別の行）。
- 使用量 = レシピの1人分の量 × その回に作る人数分（作り置きは2）。基準人数（`baseServings: 1`）、使用量、購入量を別の値として持つ。
- 購入量 = 1パックの量 × パック数（入力した単位が材料の単位と一致する場合のみ）。
- 状態: `none`（未入力）／`unknown`（パック量不明。数値を推測しない）／`mismatch`（単位不一致）／`invalid`（数値不正）／`exact`（残り0）／`leftover`（残りあり）／`short`（不足）。不足量は切り下げずにそのまま表示する。
- **自宅の食材**は量が不明なため `leftover`・`shortage` を常に `null` とし、計算しない。初期状態は「足りるか未確認」で、「自宅分で足りる」「足りないので買い足す（量を入力）」を利用者が選ぶ。買い足した場合も自宅分が不明なため残りは計算しない。
- 献立の交換で使わなくなった購入済み食材は、必要量0・購入量がそのまま残りとして表示する。
- 調味料・主食（`調味料`・`主食` カテゴリ）は買い物リストに含めるが、使い切りは求めない。傷みやすい食材（`肉・魚`・`野菜`・`豆腐`・`乳製品`）を使い切りの対象とする。
- 価格は扱わない。節約額などの金額は表示しない。

| 購入量 | 使用量 | 表示 |

## 献立の組み立て（`js/planner.js`）

評価値（小さいほど良い）で候補を比べる。

1. 条件違反（同じ料理の繰り返し禁止、調理時間、作り置き不可の料理）は事実上選ばれない重さ。満たせない場合は**条件を緩めずに失敗を返し、前の献立を残す**。
2. 入力した購入量に対する、傷みやすい食材の余り（25 × 余り/購入量）と不足（5 + 25 × 不足/購入量）。
3. 「今回使う」と指定した自宅の食材が献立に入らない場合の重み。
4. 傷みやすい食材の使い回し（2回目以降の利用を加点）と、食材が増えることへの小さな重み（追加購入の少なさだけを最優先にしない）。購入量の入力後は、まだ購入予定にない食材をやや避ける。
5. 定番と新しい料理のバランス（記録がある場合のみ）。
6. 「作り直す」で別案が出るための小さな乱数（シード固定で再現可能）。

探索: 1日目を固定した貪欲法で数案を作り、1日ずつの入れ替え・作り置きの統合と分割で改善し、最も良い案を採用する。組み直しでは現在の献立からの改善案も候補に含める。

## 保存（localStorage）

| キー | 内容 |
| --- | --- |
| `gohan-keikaku-v1` | 既存の「おまかせ献立」。**変更しない** |
| `gohan-keikaku-favorites-v1` | 既存のお気に入り。読むだけ |
| `gohan-keikaku-usekiri-v1` | 使い切り計画（条件・料理・自宅の食材・献立・購入量・自宅食材の選択・AI提案の料理） |
| `gohan-keikaku-history-v1` | 「作った」の記録（料理IDごとの回数と最終日） |

既存データの移行は不要（新しいキーを使うため）。保存データが壊れていても初期状態で始め、既存キーには触れない。保存されたAI提案は、読み込みのたびに検証し直す。

## 残る食材の保存案

- 冷凍「できる」設定なら冷凍の案、「できない」設定なら冷凍を含まない冷蔵の案を示す。
- **保存できる日数は表示しない**（根拠のない断定をしない）。購入時の表示と食材の状態の確認を促す。
- その残量だけで1人分を作れる登録済みの料理（献立にない料理）を最大3品示す。

## AI提案の検証（`js/ai.js`）

バックエンドから受け取る形式（schemaVersion 1）:

```json
{
  "schemaVersion": 1,
  "recipes": [
    {
      "name": "料理名",
      "type": "和食|洋食|中華",
      "time": 20,
      "hot": false,
      "ingredients": [{ "name": "鶏むね肉", "amount": 150, "unit": "g", "category": "肉・魚" }],
      "steps": ["…"]
    }
  ]
}
```

除外する条件: 形式不正、料理名なし、ジャンル・調理時間・辛さの不正、材料2〜20品の範囲外、扱えない単位、0以下や過大な数量（1人分の上限を単位ごとに設定）、売場カテゴリ不正、材料の重複、手順2〜12の範囲外、**材料が手順に出てこない**、**肉・魚・卵があるのに火の通りの確認がない**、鶏・豚・ひき肉を生や半生で食べる記述、加熱後の長時間常温放置、調理時間の条件超過。

受け入れた料理も「AI提案・未検証」と表示し、栄養値は「未計算」（AIが返した数値は捨てる）、画像は代替表示、保存目安は「確認されていない」とする。プログラムのチェックは安全性の保証ではないため、人による確認・試作が必要であることを詳細画面に表示する。
