## 1. 依頼内容

献立・買い物Webアプリ「ごはん計画」を、以下の要件に沿って改善する。依頼者はプログラミングの専門知識がないため、技術的な調査・設計・実装・テストを主体的に進める。費用が発生する契約、APIキーの発行、重要な構成変更は事前に説明・確認する。

## 2. サービスの目的

**対象利用者**: 都市部で働く、一人暮らしの人。

**解決したい課題**
- 毎日の献立と買い物を考えるのが負担
- 大容量パックを買うと、食材を余らせてしまう
- 自宅にある食材をうまく使えない
- 似た料理ばかりになり、新しい料理を作る機会が少ない

**提供する価値**: 食べたい料理を起点に、購入する食材を複数の料理で使い回し、買い物と献立を考える負担を減らす。定番料理を中心に、ときどき新しい料理を楽しめる。節約は、最安値の商品を探すことよりも、食材を捨てないことで結果的に食費を抑えることを重視する。

**将来の事業目標**: まいばすけっとに「お客様の買い物体験を向上させるサービス」として提案できるものを目指す。現段階では、提携・商品情報へのアクセス・価格や在庫の連携はない。公式サービスと誤認させる表示をしない。

## 3. 最初の試作品の対象範囲

まずは依頼者自身が日常的に使い、価値を検証する。

| 項目 | 決定内容 |
| --- | --- |
| 対象人数 | 一人暮らし向け。初版は1人分を中心に設計 |
| 対象の食事 | 夕食の主菜1品 |
| 計画期間 | 1〜7日から自由に選択 |
| 開始方法 | 最初に食べたい料理を選ぶ |
| 献立の傾向 | 定番中心、ときどき新しい料理 |
| 提案方式 | 生成AIを利用し、新しいレシピも提案 |
| 店舗商品との連携 | 初版では行わない |
| 食材 | 一般的な食材を扱う |
| 栄養 | 参考表示。栄養条件による最適化は今回の中心にしない |
| アレルギー | 初版では自動判定せず、利用者が材料を確認 |
| 利用者登録・課金 | 初版の必須範囲に含めない |

既存の人数変更など、利用できる機能を安易に削除しない。ただし、初版の使い切り計画は1人分を主な検証対象にする。

## 4. 基本の利用フロー

**Step 1：条件を設定する** — 計画日数（1〜7日）、調理にかけられる時間、冷凍できるか、作り置きを希望するか・可能か、同じ料理を繰り返してもよいか。調理時間や保存方法をサービス側で一律に決めない。

**Step 2：食べたい料理を選ぶ** — 最初の入口は「買いたい食材」ではなく、食べたい料理とする。選んだ料理で必要になる食材を基に、残りの日の献立を提案する。料理の選び方は、既存レシピ検索を活用するなど、実装側で使いやすい方法を設計する。

**Step 3：自宅の食材を入力する**
- 食材名だけで入力できる
- その中から、今回使いたい食材を指定する
- 残量と消費期限の入力は必須にしない
- 自宅の残量を確認する追加質問は行わない
- 提案された必要量を見て、利用者が不足分を調整する

重要：食材名だけでは、在庫が十分にあると判断できない。「自宅にあるので購入不要」と無条件に処理しない。必要量を表示し、不足する場合に買い物内容を調整できるようにする。

**Step 4：献立と買い物リストを仮作成する** — 選んだ料理を含めた献立を作る。自宅の使いたい食材も考慮する。食材を複数の料理で使い回す。料理の幅を広げるため、別の食材の追加購入も提案してよい。追加食材の少なさだけを最優先にはしない。定番中心に、ときどき新しい料理を組み込む。「未経験の料理」と断定するには調理履歴が必要なので、履歴がない段階でそのような断定をしない。

**Step 5：買い物リストでパック量を入力する** — 献立を仮作成した後、利用者が購入するパックの量を入力する（例：鶏肉 1パック300g、豚肉 1パック250g、キャベツ 半玉、豆腐 1丁300g）。入力のしやすさと、計算可能な単位の扱いを設計する。

**Step 6：パック量に合わせて献立を組み直す** — 入力された購入量を基に、食材の余りを別の日の料理へ振り分ける。使い切りを優先する対象は肉、魚、野菜、豆腐など傷みやすい食材。調味料や米などは期間内に使い切ることを要求しない。ただし、調味料も購入対象として買い物リストに含める。

**Step 7：確認・変更する** — その日の料理だけ交換する／献立全体を作り直す、の両方を用意する。料理を交換した場合は、買い物リストと食材の使用量・残量も再計算する。最初に選んだ料理を変更時にも固定するかは未決定。まずは「最初の料理を残して他の日を組み直す」を実装案として検討し、仕様に明示する。

**Step 8：残る食材を確認する** — 期間内に使い切れない場合は、残る食材、残る量、保存・冷凍の案を示す。使い切れないことを隠したり、「使い切り」と表示したまま残量を省略したりしない。冷凍不可の設定なら、冷凍を前提にした解決策を出さない。保存案には食材の状態や調理方法に応じた確認が必要であり、安全な保存期間を根拠なく断定しない。

## 5. 計算上の重要ルール

生成AIの文章だけで「使い切れます」と判断しない。AIは料理・献立の案を作り、使用量と残量はプログラムで計算する。

- 食材名を正規化して合算する
- 同じ食材でも、単位の整合性を確認する
- g・ml・個・丁・玉などを根拠なく相互変換しない
- 量が不明な「1パック」を勝手に300gとみなさない
- 材料数量、基準人数、購入量を区別する
- 在庫不足や購入量不足を明示する
- 料理交換後も計算を更新する

自宅の食材は残量未入力のため、購入食材と同じ精度で残量計算できない。その区別をデータと画面の両方で維持する。

**想定する確認例**: 購入量が鶏肉300gで、献立内の使用量が120g・100g・80gなら、残量は0g。料理を交換して合計使用量が260gになった場合、残り40gを表示する。合計必要量が350gになった場合、50gの不足を表示するか、献立を再調整する。数量を黙って切り下げない。価格を入力・取得していない段階で、「○円節約できた」などの金額を生成しない。

## 6. 生成AIに関する要件

- AI APIは安全なバックエンド経由で呼び出す
- APIキーをブラウザ・localStorage・公開GitHubへ保存しない
- AIの出力は構造化し、データ形式と数量を検証する
- 材料と工程の不一致、条件違反、不正な数量を検出する
- 調理方法の安全性を確認する仕組みを設ける
- AIによる安全性の自己申告だけを保証に使わない
- AI APIの障害・応答不正・上限超過を利用者に知らせる
- 制約に合う献立が作れない場合、制約を黙って無視しない

**栄養値**: AIが推測した数値を正確な栄養情報として表示しない。既存の60品は未検証の参考値であることを維持。新規AIレシピは計算根拠がなければ「未計算」とする。根拠のない数値で既存データを埋めない。

**導入前に決めること（未決定）**: 利用するAIサービス・モデル、バックエンドの配置とホスティング、API利用費の上限、公開時の利用制限・費用管理、必要な認証や不正利用対策。AIを使いたいという回答は、有料契約や無制限のAPI課金への承認ではない。既存のGitHub Pagesだけでは安全なAI API接続は完結しないため、追加構成と費用を説明すること。

## 7. 今回の成功基準

最も重視するのは「献立や買い物を考える時間が減り、今まで作ったことのない料理を作れて楽しい」体験。最初は依頼者自身が利用して検証する。

確認する項目: 食べたい料理から計画を作り始められるか／パック量の入力と献立の組み直しが分かりやすいか／献立と買い物を考える負担が減るか／食材の使い道と残量が理解できるか／新しい料理を無理なく試せるか。数値の目標値は未決定。達成していない効果を宣伝文句として断定しない。

## 10. 開発の進め方

1. 最新のコードとPRの状態を確認する
2. この要件定義をリポジトリ内に保存する
3. 画面の流れと食材数量のデータ構造を整理する
4. AI接続に必要な追加構成・費用・公開範囲を説明する
5. 食べたい料理選択、仮献立、パック量入力、再計画の流れを実装する
6. AI出力の検証と、プログラムによる数量計算を実装する
7. 献立交換、在庫の手動調整、残量・保存案の表示をつなぐ
8. 自動テストとブラウザテストを実施する
9. 作業ブランチからPRを作成し、日本語で報告する

画面だけを作った段階や、固定データを返す段階で「AI献立・使い切り機能が完成」と報告しない。

**必須の検証**: 計画日数1〜7日／最初に選んだ料理の扱い／パック量変更後の再計算／同じ食材の合算／単位不一致・数量不明への対応／不足量・残量の表示／自宅食材の残量を勝手に推測しないこと／料理単体交換と献立全体の再作成／繰り返し・調理時間・冷凍・作り置き条件／AI応答の不正・失敗時の表示／保存済みデータとの互換性／PC・スマホでの操作

## 11. 初版で広げすぎないこと

必須範囲に含めない: 朝食・昼食・弁当／主菜・副菜・汁物をそろえた献立／店舗別の価格・在庫連携／バーコード・レシート読み取り／アレルギーの自動判定／正確な栄養・PFC最適化／会員課金／レシピ数を増やすこと自体を目的にした拡張。まず、食べたい料理から始まり、パック量を反映して使い回し計画を作れる体験を成立させる。

## 12. 報告・承認のルール

- 変更内容、検証結果、未解決事項、公開状態を日本語で報告する
- 機密情報を公開しない
- 権利不明の画像・レシピを転載しない
- 有料契約やAPIキー発行を勝手に進めない
- 重要な構成変更は事前に説明する
- 公開作業は承認範囲を確認し、実施後は本番の動作まで確認する
- 未決定事項は、決定済みの要件として扱わない
